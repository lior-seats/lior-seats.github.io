Kubernetes SSL Certificate Monitoring: Track TLS Expiry in Your Cluster

cert-manager renews. Until it doesn't. Here's how to know when your K8s TLS certs are silently expiring.

Kubernetes handles SSL certificates differently from traditional web servers. Instead of cert files on disk, TLS credentials live inside cluster secrets. cert-manager automates renewals. Ingress controllers handle TLS termination. The whole system looks automated — until a renewal silently fails and your service goes down with an expired certificate that nobody noticed.

This guide covers how Kubernetes TLS certificate monitoring actually works: inspecting secrets, watching cert-manager resources, checking ingress TLS status, and getting external visibility on what your cluster is actually serving.

How Kubernetes stores TLS certificates

In Kubernetes, TLS certificates are stored as Secrets of type kubernetes.io/tls. These contain two fields: tls.crt (the certificate chain) and tls.key (the private key).

kubectl get secrets --all-namespaces -o json \
  | jq -r '.items[] | select(.type=="kubernetes.io/tls") | "\(.metadata.namespace)/\(.metadata.name)"'

To inspect the expiry date of a specific TLS secret:

kubectl get secret my-tls-secret -n my-namespace \
  -o jsonpath='{.data.tls\.crt}' \
  | base64 -d \
  | openssl x509 -noout -enddate -subject

To check days remaining for all TLS secrets in a namespace:

#!/bin/bash
NAMESPACE=${1:-default}
kubectl get secrets -n "$NAMESPACE" --field-selector type=kubernetes.io/tls \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}' \
| while read secret; do
    expiry=$(kubectl get secret "$secret" -n "$NAMESPACE" \
      -o jsonpath='{.data.tls\.crt}' \
      | base64 -d \
      | openssl x509 -noout -enddate 2>/dev/null \
      | cut -d= -f2)
    days=$(( ($(date -d "$expiry" +%s) - $(date +%s)) / 86400 ))
    echo "$days days  $NAMESPACE/$secret  ($expiry)"
done | sort -n

Run this script across all namespaces to get a sorted list of certificates by days remaining — soonest expiry first.

cert-manager Certificate resources vs. actual TLS secrets

If you're using cert-manager, certificates are represented by Certificate custom resources. cert-manager watches these, issues certificates via an ACME or CA issuer, and stores the result in a TLS Secret. You can query cert-manager's view of certificate status:

# List all Certificate resources and their ready state
kubectl get certificates --all-namespaces

# Describe a specific certificate for renewal status and events
kubectl describe certificate my-cert -n my-namespace

The describe output shows the renewal time, last issued time, and any recent events — including renewal failures. Look for:

Status:
  Conditions:
    Type:    Ready
    Status:  True
    Reason:  Ready
  Not After:  2026-12-14T00:00:00Z
  Not Before: 2026-09-14T00:00:00Z
  Renewal Time: 2026-11-24T00:00:00Z

If Ready is False, cert-manager is actively failing to renew the certificate. The events section will show why.

cert-manager Ready: True does not mean the cert was recently renewed A certificate can be Ready: True while still approaching expiry if cert-manager hasn't attempted renewal yet (renewal begins 30 days before expiry by default). Always check Not After directly, not just the Ready condition.

Common cert-manager silent failure modes

cert-manager can fail to renew certificates without generating obvious alerts. The most common silent failure scenarios:

ACME HTTP-01 challenge failures

HTTP-01 challenges require cert-manager to serve a validation token on port 80. If your ingress is misconfigured, a NetworkPolicy blocks the ACME server, or port 80 traffic is redirected before the challenge path is served, the challenge silently times out:

kubectl describe order my-cert-order -n my-namespace
# Look for: "Error: failed to perform self check GET request"

DNS-01 challenge failures

DNS-01 challenges modify DNS records via a cloud provider API. If the API credentials in your cert-manager secret expire, the DNS provider's API rate-limits the requests, or IAM permissions change, renewals fail silently:

kubectl logs -n cert-manager deployment/cert-manager | grep -i "error\|failed\|challenge"

Issuer not ready

A ClusterIssuer that loses connectivity to the ACME endpoint (Let's Encrypt rate limit, network policy change, ACME directory URL change) will show Ready: False on the Issuer resource but won't prevent existing certificates from appearing valid until they expire:

kubectl get clusterissuer -o wide
# Check the Ready column — should be True for all issuers

cert-manager controller not running

kubectl get pods -n cert-manager
kubectl logs -n cert-manager deployment/cert-manager --since=1h | tail -50

A crash-looping cert-manager controller means no renewals are happening. Existing certificates continue serving, masking the problem until they expire.

Kubernetes Ingress TLS monitoring

Ingress resources reference TLS secrets by name. If the referenced secret expires, the ingress controller continues serving the expired cert until the secret is replaced — no error, no restart, just an expired TLS handshake for every visitor:

# List all ingresses and their TLS configuration
kubectl get ingress --all-namespaces -o json \
  | jq -r '.items[] | "\(.metadata.namespace)  \(.metadata.name)  \(.spec.tls[].secretName // "no-tls")"'

Cross-reference ingress TLS secret names against the expiry script above to prioritize which secrets matter most. An expiring TLS secret that backs a production ingress is critical. One that backs a staging environment is lower priority.

SNI and wildcard certs in K8s Kubernetes ingress controllers use SNI to route TLS to the correct virtual host. If you're using a wildcard cert (*.example.com), a single expiring secret can take down all subdomains simultaneously. Wildcard certs warrant extra monitoring attention.

Cluster-external SSL monitoring: what kubectl misses

Checking TLS secrets with kubectl tells you what's stored in the cluster. It doesn't tell you what the external world sees. The certificate that a visitor's browser negotiates depends on:

  • Which certificate the ingress controller actually loaded (it may cache the old cert after a secret update until it receives a reload signal)
  • Whether a CDN or load balancer in front of the cluster is terminating TLS with its own cert
  • Whether the SNI routing is correct for the specific hostname the visitor uses
  • Whether the cert chain is complete (intermediate CA certificates included)

An external TLS handshake check — connecting to the actual HTTPS endpoint — is the only reliable way to confirm what a visitor's browser sees:

echo | openssl s_client -connect your-k8s-service.example.com:443 \
  -servername your-k8s-service.example.com 2>/dev/null \
  | openssl x509 -noout -enddate -issuer -subject

For Kubernetes services, this should be run against the external hostname (via LoadBalancer or Ingress), not the in-cluster service IP.

Setting up Kubernetes TLS certificate monitoring alerts

For production clusters, a monitoring approach that covers all of these failure modes needs to:

  • Check external TLS endpoints — verify what the internet actually sees, not just what's in etcd
  • Alert at multiple thresholds — 30, 14, 7, and 1 day before expiry for meaningful runway
  • Cover all ingress hostnames automatically — not just the ones someone remembered to add to a spreadsheet
  • Work independently of cert-manager's health — if cert-manager is broken, monitoring should still catch the approaching expiry
  • Not require cluster access to check — an external monitoring service continues working even if the cluster is partially degraded

External SSL monitoring services check your HTTPS endpoints from outside the cluster on a regular schedule. They see exactly what your users see and alert you when expiry is approaching — regardless of whether cert-manager is healthy.
