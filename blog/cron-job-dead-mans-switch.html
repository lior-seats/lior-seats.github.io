Cron Job Dead Man's Switch: How to Know When Scheduled Jobs Stop Running

Error monitoring catches crashes. A dead man's switch catches silence — which is usually worse.

Most cron job monitoring tools work by watching for errors: an exit code above 0, an exception in the logs, a timeout. That covers a real class of failure. But there's a more common problem those tools miss entirely: the job just stops running. No error. No crash. It simply stops being scheduled, stops executing, stops producing output. And nobody knows.

A dead man's switch inverts the model. Instead of alerting you when something goes wrong, it alerts you when something stops happening. The job is expected to check in on every run. If the check-in doesn't arrive within a grace period, the switch fires and sends an alert.

Why "absence of failure" is not the same as success

Most application error trackers (Sentry, Rollbar, Datadog APM) are built around the assumption that bad things produce signals. A crash produces a stack trace. A slow query produces a slow-query log. A 500 produces an error rate spike.

Cron jobs break this assumption. When a cron job stops running, it produces nothing. Consider these scenarios:

  • The scheduler process crashes. If your cron daemon, Kubernetes CronJob controller, or Heroku Scheduler process restarts with an empty queue, your jobs simply stop. No error is emitted. The next run date is never set.
  • The server is replaced. During an infrastructure migration or auto-scaling event, the old server with your crontab is retired. The new server has no cron configuration. Jobs disappear.
  • A deployment breaks the environment. A new deploy changes a dependency or removes an environment variable. The job script errors on startup — before it can write to any error log — and the scheduler treats it as a successful (if empty) run and moves on.
  • The job takes longer than its interval. The scheduler skips the next run to avoid overlap. Then skips again. Eventually the scheduler blacklists the job as too slow. Silence.

In all of these cases, your error tracking shows zero errors. Your application metrics look healthy. Meanwhile, your nightly billing sync, your daily report, your cleanup job — all stopped running days ago.

The pattern to internalize: An absence of errors is not evidence of a running job. It is evidence of no errors. Those are very different things.

How a dead man's switch works

The term comes from safety engineering. A dead man's switch is a control that requires a human operator to actively confirm they are alive and present. If the operator stops responding — falls asleep, has a medical event, loses consciousness — the switch triggers a safety action.

For cron jobs, the mechanism works like this:

  1. You register a monitor for a job that should run on a schedule (say, every hour).
  2. At the end of each successful run, the job sends an HTTP request to a heartbeat URL — a simple curl call is enough.
  3. The monitoring service tracks the last check-in time for each monitor.
  4. If no check-in arrives within the expected window plus a grace period, an alert fires.

The job itself is responsible for reporting its success. If it stops reporting, the monitoring service assumes it stopped running — and tells you.

A concrete implementation in bash

#!/bin/bash
set -e

# Your actual job logic
/usr/local/bin/sync-billing-records.py

# Check in on success — only reached if the job above succeeds
curl -fsS --retry 3 "https://cronwatch.example.com/heartbeat/YOUR_TOKEN" > /dev/null

The set -e ensures that if sync-billing-records.py fails, the script exits immediately — the heartbeat call is never reached. If the heartbeat doesn't arrive, the monitoring service alerts you. If the script crashes before the heartbeat line, the monitoring service alerts you. If the cron daemon never runs the script at all, the monitoring service alerts you.

Three failure modes, one mechanism to catch all of them.

Setting the right grace period

Every dead man's switch implementation requires a grace period — the amount of time after a missed expected check-in before an alert fires. Set it too short and you'll get false positives when a slow job takes longer than usual. Set it too long and you'll miss real outages for hours.

A reasonable default for most jobs is the job's interval plus 25–50%. For a job that runs every hour, a 75-minute grace period means you get alerted within 15 minutes of a missed run while tolerating reasonable slowness. For a daily job, a 26-hour grace period catches a missed run within 2 hours of the next expected execution.

Adding a dead man's switch to common schedulers

crontab

# Every hour — check in after successful completion
0 * * * * /path/to/sync.sh && curl -fsS "https://your-heartbeat-url/TOKEN" > /dev/null 2>&1

The && operator ensures curl only runs if the job exits successfully. The redirect to /dev/null 2>&1 prevents the curl output from triggering a local mail notification.

Node.js (node-cron)

import cron from 'node-cron';
import fetch from 'node-fetch';

cron.schedule('0 * * * *', async () => {
  try {
    await syncBillingRecords();
    // Check in on success
    await fetch(process.env.CRONWATCH_HEARTBEAT_URL, { method: 'GET' });
  } catch (err) {
    console.error('Job failed:', err);
    // No check-in = monitoring service alerts
  }
});

Python (APScheduler)

import requests
from apscheduler.schedulers.blocking import BlockingScheduler

scheduler = BlockingScheduler()

@scheduler.scheduled_job('cron', hour='*')
def sync_job():
    sync_billing_records()  # Raises on failure
    # Check in on success
    requests.get(os.environ['CRONWATCH_HEARTBEAT_URL'], timeout=5)

scheduler.start()

GitHub Actions

- name: Run billing sync
  run: python sync_billing.py

- name: Heartbeat check-in
  if: success()
  run: curl -fsS "${{ secrets.CRONWATCH_HEARTBEAT_URL }}"

The if: success() condition ensures the heartbeat step only runs when all previous steps passed.

What happens when the check-in is missing

A good dead man's switch monitor sends an alert through whatever channel you actually check: email, Slack, PagerDuty, SMS. The alert should include:

  • Which job missed its check-in
  • When the last successful check-in was received
  • What the expected interval is
  • How long it's been since the last check-in

Armed with that information, you can diagnose in minutes: check the cron daemon, check the deployment history, look at server logs for the job's process. The monitor tells you when something stopped; you figure out why.

Dead man's switch vs. log-based monitoring

Log-based monitoring (checking for error patterns in application logs) and dead man's switches are complementary, not alternatives. Log monitoring catches errors when jobs run but behave wrongly. Dead man's switches catch the case when jobs don't run at all. Both are necessary for complete coverage.

If you can only have one: the dead man's switch catches more failure modes with less setup. You don't need to know what error patterns to look for, you don't need log aggregation infrastructure, and you're covered against scheduler-level failures that produce no application logs at all.
