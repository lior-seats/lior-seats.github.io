Free SSL Certificate Monitoring — 5 Ways to Get Expiry Alerts

From zero-setup options to a working cron job — how to get SSL expiry notifications without spending anything.

SSL certificates expire. When they do, browsers show security warnings, search engines flag your site, and payment processors refuse to connect. An expired cert on a production service typically costs hours of engineer time and real revenue. The monitoring required to prevent this is free in most cases — the gap is usually just that it was never set up.

Before choosing a monitoring approach, it's useful to know where your certificates currently stand. Check any domain's expiry right now with the free SSL Certificate Checker — no account required.

The catch with "free" SSL monitoring: Several of these approaches require setup time or ongoing maintenance. A tool that takes two hours to configure and breaks silently every few months is not actually free — the cost is engineering time. Choose the approach that matches your operational overhead budget, not just your cash budget.

1 Google Search Console (Zero Setup, Very Limited)

Google Search Console will sometimes surface HTTPS errors in its Coverage and Security reports — including issues caused by expired or invalid certificates. If you already have Search Console set up for your site, it costs nothing extra and requires no additional configuration.

How to use it: In Search Console, go to Security & Manual Actions > Security Issues. If your site has a certificate error that Google has detected, it will appear here.

The real limitation: Search Console is a reactive signal, not a proactive alert. Google has to crawl your site, detect the error, index it, and surface it in the report. This typically happens after the certificate has already expired and affected users. You're learning about an outage that already happened, not preventing one.

Search Console is useful for confirming that a cert issue impacted Google's crawling — it's not a substitute for forward-looking expiry monitoring.

Verdict: Zero cost, zero setup, zero prevention value. Use it as a signal that an SSL problem already affected your SEO, not as a way to prevent expiry.

3 Self-Hosted certbot/cron + Email (Technical, Unlimited Domains)

If you manage your own servers and use Let's Encrypt with certbot, you can set up a cron job that checks certificate expiry daily and emails you when any cert is within a configurable threshold. This gives you unlimited domains and configurable advance windows at zero cost beyond your server's existing operational overhead.

A minimal working script:

#!/bin/bash
# ssl-expiry-check.sh
# Run daily via cron; alerts when any domain cert expires within ALERT_DAYS

DOMAINS=("yourdomain.com" "api.yourdomain.com" "anotherdomain.com")
ALERT_DAYS=30
ALERT_EMAIL="ops@yourcompany.com"

for DOMAIN in "${DOMAINS[@]}"; do
  EXPIRY=$(echo | openssl s_client -connect "$DOMAIN":443 \
    -servername "$DOMAIN" 2>/dev/null \
    | openssl x509 -noout -enddate 2>/dev/null \
    | cut -d= -f2)

  if [ -z "$EXPIRY" ]; then
    echo "SSL check failed: $DOMAIN (could not retrieve cert)" \
      | mail -s "SSL error: $DOMAIN" "$ALERT_EMAIL"
    continue
  fi

  EXPIRY_EPOCH=$(date -d "$EXPIRY" +%s 2>/dev/null \
    || date -j -f "%b %d %T %Y %Z" "$EXPIRY" +%s)
  DAYS=$(( (EXPIRY_EPOCH - $(date +%s)) / 86400 ))

  if [ "$DAYS" -le "$ALERT_DAYS" ]; then
    echo "$DOMAIN SSL expires in $DAYS days ($EXPIRY)" \
      | mail -s "⚠️ SSL expiry warning: $DOMAIN ($DAYS days)" "$ALERT_EMAIL"
  fi
done

Add to crontab to run daily at 8am:

0 8 * * * /path/to/ssl-expiry-check.sh 2>&1 | logger -t ssl-check

Where this breaks in practice:

  • The mail command requires a working outbound mail setup — often broken or spam-filtered on cloud VMs
  • If the cron job itself fails (permission issue, openssl version mismatch, cron daemon down), it fails silently
  • No dashboard — you have to run the script manually to see the current state of all certs
  • No alerting to Slack or other channels without additional scripting

A more reliable variant replaces mail with a webhook POST to a Slack channel or a generic HTTP endpoint, eliminating the mail server dependency entirely.

Verdict: Powerful and unlimited, but requires setup, a working mail or webhook setup, and periodic maintenance. Excellent fit for teams that already run their own infrastructure and want complete control.

4 Browser Bookmark Reminder (Low-Tech, Manual)

The lowest-tech approach: bookmark the SSL Certificate Checker with a reminder to check it monthly. Set a recurring calendar event — "check SSL certs" — and use the tool to verify each domain's expiry date when it fires.

This sounds almost too simple to be worth mentioning, but it has a real niche: environments where you can't install monitoring tools, don't have server access, or are managing only one or two domains for a non-technical client.

Why it works:

  • Zero setup, zero infrastructure
  • Works for any domain regardless of your access to the underlying server
  • No vendor dependency

Why it fails:

  • It requires the human to remember to do it — exactly the failure mode that causes production cert expirations in the first place
  • Doesn't scale beyond a handful of domains
  • A missed calendar event means missed monitoring
Verdict: Only reliable for 1–2 domains where you can pair it with a strong calendar habit. For anything more, automate.
