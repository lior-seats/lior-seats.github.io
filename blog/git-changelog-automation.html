Why your git history is useless to stakeholders — and how to auto-generate changelogs that aren't

47 commits: "fix typo", "WIP", "more fixes", "FINALLY", "ugh". The sprint ended. The PM wants to know what shipped.

Every two weeks it's the same conversation. Sprint review is in an hour. The PM opens a ticket: "Can someone update the changelog?" You open a terminal:

a3f1d9c fix typo
b8e2c14 WIP
c91a7e5 more fixes
d4b3f22 lol
e5c8d11 FINALLY
f7a9e33 add retry logic to payment handler
g2d4b56 forgot to add tests
h8e1c79 tests passing now hopefully
i3f7a92 implement user export feature
j9b2d15 cleanup

You spend 25 minutes reading diffs, reconstructing intent, and writing a changelog that should have taken three minutes. Then it happens again next sprint.

The problem isn't the developers — commit messages are written under pressure for the author's short-term memory, not for stakeholders reading them two weeks later. The solution isn't telling developers to write better commits (you've tried). It's automating the translation layer between git history and human-readable changelog.

Why commit messages are structurally bad as changelogs

Commit messages are optimized for one reader (the author) at one moment in time (the moment of writing). They're useful for git blame, for understanding the context of a change, for bisecting a bug. They're almost useless for external communication.

The core problems:

  • Granularity mismatch. A single feature might span 20 commits. A changelog needs one entry. Mechanical extraction produces 20 items when you need one.
  • Audience mismatch. "Refactor payment handler to use async/await instead of promise chains" is a meaningful commit message. "Payments are now more reliable" is what goes in the changelog.
  • Noise ratio. WIP commits, fixup commits, merge commits, and typo fixes are legitimate parts of the git workflow. They're noise in a changelog.
  • Context loss. The commit that says "fix the thing from yesterday" makes perfect sense when you wrote it. It's incomprehensible to anyone else.
What about Conventional Commits? Conventional Commits is a great discipline for structured commit history: feat: add user export, fix: payment retry logic, chore: update dependencies. It solves the noise/signal problem for teams that enforce it. But most codebases weren't built with it, and "rewrite your commit discipline" is a harder sell than "automate the translation."

The approach below works with both — Conventional Commits gives the LLM better input, but the LLM also handles the unstructured case well.

Current approaches and why they fall short

git log --oneline → copy-paste → rewrite

This is what most teams do. It works but it's slow, it doesn't scale to frequent releases, and the quality depends entirely on whoever writes it that day.

auto-changelog and similar tools

Tools like auto-changelog, conventional-changelog, and release-it parse commit messages mechanically and template them into a CHANGELOG.md. This works well for Conventional Commits codebases — it produces consistent output, automates the file update, and runs in CI. But the output is still commit-message text, just formatted differently. "fix: payment retry" becomes "- fix: payment retry" in the changelog. The audience mismatch and noise problem remain.

GitHub Releases

GitHub's "Auto-generate release notes" feature compares commits since the last tag and produces a list of PR titles and merged PRs. Better than raw commits, but still technical and mechanical. Fine for developer audiences; poor for product stakeholders, users, or public-facing changelogs.

The AI-powered approach: git log → LLM → readable changelog

The insight: language models are exceptionally good at the specific task of summarizing technical text for a non-technical audience. "Summarize these 47 commits into what a user cares about" is a task that takes a developer 20 minutes and an LLM about 3 seconds.

Here's a Node.js script that does exactly this:

#!/usr/bin/env node
// generate-changelog.js
// Usage: node generate-changelog.js [--since "7 days ago"] [--since-tag v1.2.3]
// Requires: OPENAI_API_KEY in env

const { execSync } = require('child_process')
const https = require('https')

const args = process.argv.slice(2)
const sinceIndex = args.indexOf('--since')
const sinceTagIndex = args.indexOf('--since-tag')

let gitLogCmd
if (sinceTagIndex !== -1) {
  const tag = args[sinceTagIndex + 1]
  gitLogCmd = `git log ${tag}..HEAD --pretty=format:"- %s (%an)" --no-merges`
} else {
  const since = sinceIndex !== -1 ? args[sinceIndex + 1] : '7 days ago'
  gitLogCmd = `git log --since="${since}" --pretty=format:"- %s (%an)" --no-merges`
}

const commits = execSync(gitLogCmd, { encoding: 'utf8' }).trim()

if (!commits) {
  console.log('No commits found in the specified range.')
  process.exit(0)
}

const prompt = `You are a technical writer. Below is a list of git commits from a software project.

Generate a concise, user-friendly changelog in this exact format:

## What's new
[2-4 bullet points about major new features or improvements. User-facing language only.]

## Bug fixes
[Bullet points for bug fixes. Skip if none.]

## Under the hood
[1-2 bullets for technical improvements users might notice indirectly. Omit internal refactors.]

Rules:
- Skip WIP, typo, cleanup, and merge commits entirely
- Combine related commits into single bullet points
- Write for a non-technical audience (product managers, users)
- If a section has nothing meaningful, omit it
- Keep each bullet to one sentence

Commits:
${commits}

Changelog:`

const requestBody = JSON.stringify({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: prompt }],
  max_tokens: 500,
  temperature: 0.3
})

const options = {
  hostname: 'api.openai.com',
  path: '/v1/chat/completions',
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ***`,
    'Content-Length': Buffer.byteLength(requestBody)
  }
}

const req = https.request(options, (res) => {
  let data = ''
  res.on('data', chunk => data += chunk)
  res.on('end', () => {
    const response = JSON.parse(data)
    if (response.error) {
      console.error('OpenAI error:', response.error.message)
      process.exit(1)
    }
    const changelog = response.choices[0].message.content.trim()
    const today = new Date().toISOString().split('T')[0]
    console.log(`# Changelog — ${today}\n\n${changelog}\n`)
  })
})

req.on('error', (err) => {
  console.error('Request error:', err.message)
  process.exit(1)
})

req.write(requestBody)
req.end()

Usage:

OPENAI_API_KEY=sk-... node generate-changelog.js
# Or since a specific release tag:
OPENAI_API_KEY=sk-... node generate-changelog.js --since-tag v1.4.2

Typical output for a sprint worth of commits:

# Changelog — 2026-09-21

## What's new
- Users can now export their account data as a CSV from the settings page
- Payment retries now happen automatically when a card charge fails — no more manual retry requests to support
- Dashboard loading time reduced by ~40% on large accounts

Cost for a typical sprint: under $0.01. GPT-4o-mini is priced at $0.15/1M input tokens; a full sprint of commits is ~1,000 tokens.

Automate it with GitHub Actions

Run this on every merge to main so the changelog is always up to date:

# .github/workflows/changelog.yml
name: Generate changelog

on:
  push:
    branches: [main]

jobs:
  changelog:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # full history needed for git log

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Generate changelog
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
        run: |
          node generate-changelog.js --since "$(git log -1 --before=1.day --format=%ci)" \
            >> CHANGELOG.md

      - name: Commit changelog
        uses: stefanzweifel/git-auto-commit-action@v5
        with:
          commit_message: "chore: update changelog [skip ci]"
          file_pattern: CHANGELOG.md

Add OPENAI_API_KEY to your repository secrets (Settings → Secrets → New repository secret). The workflow generates and commits a changelog entry on every merge, automatically, with no developer involvement.

✅ What you get from this setup An always-current CHANGELOG.md that reads like a product person wrote it, generated from every merge, costing less than a coffee per year. PMs can bookmark the file. Users can subscribe to the releases RSS feed. Nobody needs to write anything.

Where this approach hits limits

The script above solves the "weekly changelog" problem for a single repo. The gaps appear as your product scales:

  • Multi-repo products. A monorepo is straightforward. Microservices with 10 separate repos need 10 changelog runs, then someone needs to synthesize them into a product changelog. The script can't do that automatically.
  • Jira/Linear integration. Ticket references in commit messages (PROJ-1234) contain more context than the commit message itself. A good changelog pulls the ticket title and description — not just the commit.
  • Push to stakeholders. Generating a CHANGELOG.md is step one. Getting it to the PM via Slack, to users via email, to customers via an embedded widget — that's a separate system.
  • Version and semver management. When to bump major vs. minor vs. patch based on what changed requires either Conventional Commits or manual decisions.
